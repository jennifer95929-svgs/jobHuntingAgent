# 智能求职平台 — 设计方案

## 3. 模块设计

### 3.1 数据层 (Data Layer)

#### 3.1.1 数据库: SQLite → `data/platform.db`

| 表 | 字段 | 说明 |
|----|------|------|
| `companies` | id, name, industry, scale, financing_stage, listed, business_desc, website, qichacha_url, first_seen, last_updated | 公司基础信息（从企查查获取） |
| `position_snapshots` | id, company_id, date, ai_position_count, total_position_count, keyword, source | AI岗位数量快照（每日回查） |
| `daily_applies` | id, date, company_id, job_id, title, salary, city, keyword | 今日投递记录 |
| `daily_analyses` | id, date, company_id, market_sector, stock_info, strengths(JSON), weaknesses(JSON), match_score, ai_trend, summary, interview_tips(JSON) | 每日公司深度分析 |
| `conversion_log` | id, company_id, job_id, date, stage, action, detail | 转化漏斗记录（每个节点一条） |
| `conversion_stages` | id, company_id, job_id, current_stage, updated_at | 当前阶段汇总 |
| `daily_reports` | id, date, company_count, applied_count, conversion_stats(JSON), report_html | 每日日报存档 |

**转化阶段枚举**: `applied → read → replied → interview_invited → interview_done → offer → rejected → withdrawn`

#### 3.1.2 数据流

```

    │       └── 无回复 → 关闭聊天对话框
    │
    ├──→ 写入 daily_applies + conversion_log (stage=applied)
    │
    ├──→ 在 面试准备/03_公司面试/{公司名}/ 创建目录结构

    │      │   ├── 02_市场板块分析.md         ← 企查查+LLM

              │

              │      - 搜索该公司当前AI岗位数量
              │      - 对比上次记录 → 趋势判断

### 3.2 企查查爬虫 (Qichacha Scraper)

#### 目标页面

- 企查查搜索: `https://www.qichacha.com/search?key={company_name}`
- 公司详情页: `https://www.qichacha.com/company_getdetail?unique={id}`

#### 提取字段

| 字段 | 选择器/方式 | 优先级 |
|------|-------------|--------|
| 行业 | 详情页 "所属行业" | 高 |
| 企业规模 | 详情页 "参保人数" / "人员规模" | 高 |
| 融资轮次 | 详情页 "融资信息" | 中 |
| 上市信息 | 详情页 "上市信息" / 标签 | 高 |
| 主营业务 | 详情页 "经营范围" 摘要 | 高 |
| 注册时间 | 详情页 "成立日期" | 低 |
| 注册地址 | 详情页 "企业地址" | 低 |
| 竞品信息 | 详情页 "竞品信息" 列表 | 中 |

#### 反爬策略

- 复用现有 Chrome 实例（patchright/agent-browser）
- 独立的 qichacha cookie 缓存
- 请求间隔 3-5s，随机 user-agent
- 单日限制 ≤ 100 次查询

### 3.3 AI 岗位追踪器 (Position Tracker)

#### 工作原理

```
每日触发:
  for each company in today_applies:
    1. 搜索 keyword="AI产品经理 site:zhipin.com {company}"
    2. 或直接查 BOSS 公司主页: zhipin.com/gongsi/{company_id}.html
    3. 爬取该公司所有在招岗位
    4. 统计 AI/ML/DL/NLP/LLM 相关岗位数量
    5. 写入 position_snapshots
    6. 计算趋势: 本次数量 - 上次数量 → 增多/减少/持平
```

#### 趋势可视化

- 折线图: 横轴=日期, 纵轴=AI岗位数量
- 标注: 投递日期、HR回复日、面试日

### 3.4 LLM 分析引擎 (Analysis Engine)

#### 分析流程

```
Input: company_data (from 企查查) + JD + resume

Step 1 - 市场板块分析
  Prompt:
    "分析{公司名}所属行业板块、市场地位、
     主要竞争对手、在AI领域的布局、
     以及该公司的增长潜力"

Step 2 - 长板/短板分析
  Prompt:
    "结合我的简历({resume})和该公司{JD}、
     分析我入职该公司的长板优势在哪里、
     短板和风险在哪里、
     给出1-5分的综合匹配度评分"

Step 3 - 面试建议
  Prompt:
    "基于以上分析，给出面试准备建议、
     该公司业务中最值得深入了解的方向、
     可能被问到的难点问题"
```

#### 成本优化

- 每家公司的3个步骤合并为1次 LLM 调用（通过结构化输出）
- 分层调用（见 3.8）：L1 = 快速分析 1pass，L3 = 深度分析 3pass
- 复用已有分析结果（30天内不重复分析）

### 3.5 转化漏斗追踪 (Conversion Tracker)

#### 目标

追踪每家公司从投递到Offer的完整转化链路，找到卡点和优化方向。

#### 实现方式

```
投递时              → conversion_log: applied
聊天页面检测到HR已读  → conversion_log: read
检测到HR回复消息     → conversion_log: replied  + 记录HR话术
用户标记"约面"      → conversion_log: interview_invited (手动或自动识别)
用户标记"面试完成"   → conversion_log: interview_done + 记录面试题
用户标记"Offer/拒信" → conversion_log: offer/rejected
```

#### 转化率看板 (ECharts)

```
┌───── 转化漏斗 ───────────────────────┐
│  投递: 50  (100%)                     │
│  ████████████████████████████████     │
│  已读: 30  (60%)                      │
│  ██████████████████                   │
│  回复: 15  (30%)                      │
│  ██████████                           │
│  约面: 5   (10%)                      │
│  ████                                 │
│  Offer: 2  (4%)                       │
│  ██                                   │
└────────────────────────────────────────┘
```

#### 卡点分析

| 流失环节 | 可能原因 | 优化动作 |
|---------|---------|---------|
| 已投→已读低 | 活跃度不足 / 简历不匹配 | 调整打招呼话术 / 优化简历关键词 |
| 已读→回复低 | 吸引力不够 | A/B测试打招呼模板 |
| 回复→约面低 | 聊天中暴露短板 | 聊天话术分析 + 针对性训练 |
| 面试→Offer低 | 面试表现不足 | 面试复盘 + 薄弱点针对性提升 |

### 3.7 分层分析策略 (Layered Analysis)

#### 为什么需要分层

50家/天的投递量下，全量深度分析不可行。分析成本必须跟回报成正比。

#### 四层模型

| 层级 | 触发时机 | 分析内容 | LLM调用 | 写入目标 |
|------|---------|---------|---------|---------|
| **L0** | 投递时即时 | JD关键词提取、公司名标记 | 0 (规则) | SQLite daily_applies |
| **L1** | 投递后批量(50家) | 企查查基础数据 + LLM快速分析(1pass) | 1次/家 | companies表 + 01_JD能力模型分析.md |
| **L2** | HR回复后 | 竞品分析 + 聊天话术分析 + 匹配度详评 | 2次/家 | 补充分析到 daily_analyses |
| **L3** | 约面确认后 | 面试速查卡 + 项目拆解 + 模拟面试题 + 产品体验 | 3次/家 | 03_面试速查卡.html + 项目拆解/ |

**核心原则**: L1 50家全量分析(预算 ≈ ¥5)，L2/L3只投给有转化潜力的公司。

#### 各家预估耗时

| 层级 | 耗时/家 | 50家总量 | 说明 |
|------|--------|---------|------|
| L0 | ~0s | ~0s | 规则匹配 |
| L1 | ~5s (企查查) + ~3s (LLM) | ~7min | 50家并行，实际更短 |
| L2 | ~10s (LLM) | 仅回复后触发(~15家≈2.5min) |
| L3 | ~60s (深度分析) | 仅约面后触发(~5家≈5min) |
| **总计** | | **~15min/天** | 自动化跑完，无需人工介入 |

## 6. 关键设计决策

| 决策 | 选项 | 选择 | 理由 |
|------|------|------|------|
| 数据库 | JSON / SQLite | **SQLite** | 支持 JOIN、趋势查询、外部依赖少 |
| 企查查方式 | 自建爬虫 / 付费API | **自建爬虫** | 免费且可控；复用现有 CDP 架构 |
| 分析触发 | 投递后同步 / 定时 | **投递后同步** | 投递完立即出日报，无需等待 |
| 分析层次 | 全量深度 / 分层 | **分层(L1/L2/L3)** | 50家/天 + 深度分析 = 15min，刚好回本 |
| 转化追踪 | 人工维护 / 自动 | **自动注入钩子** | 投递、chat检测自动打点，无需手动 |
| 面试准备 | 平台内独立 / 复用现有目录 | **复用面试准备/** | 已有结构成熟，不破坏习惯 |
| 日报形式 | 本地HTML / 部署Web | **本地HTML** | 单用户、可打开、可存档 |
| LLM分析频率 | 每次 / 缓存30天 | **缓存30天** | 同一公司短期内不重复分析 |
| 岗位趋势检测 | 仅今日 / 每日回查 | **仅投递当日回查** | 减少请求量，后续人工可手动刷新 |
| 聊天分析 | 手动看 / 自动分析回复率+话术 | **自动汇总到漏斗看板** | 可量化话术效果 |

## 7. 风险和缓解

| 风险 | 缓解措施 |
|------|---------|
| 企查查反爬封IP | 复用BOSS的Chrome实例和IP，间隔3-5s |
| LLM分析质量不稳定 | 结构化输出+JSON Schema约束 |
| SQLite并发写入冲突 | 使用 WAL 模式 + 顺序写（单线程够用） |
| 日报页面打开慢（图片/CDN） | ECharts 用本地 fallback，CSS内联 |
| 50家公司分析耗时过长 | 分层分析: L1全量(7min) + L2/L3按需 |
| 面试准备目录被手动修改后与DB不一致 | 以DB为source of truth，目录只管读+写，不校验 |
| 转化阶段更新不及时 | 提供CLI命令 `python -m pipeline.converter update --company X --stage Y` 手动补录 |
